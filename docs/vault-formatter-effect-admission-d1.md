# #472 R2/B2c-D1/A0 — effect-time admission contract (source-only)

**Design and disposable tests only.** Nothing here issues runtime permits, changes the Owner Ledger, provisions identities, installs a provider broker, accesses credentials, performs HTTP, enables a Formatter Writer or deploys a service. D0 `run.claim` reserves an approved Run once; `run.status` reports a historical observation. Neither is effect authorization.

## Confirmed gap in the merged source

`DurableRunDrain.effect()` acquires the existing local `effect-drain.lock`, checks the signed grant and reserves a Worker receipt, **but does not query the Owner-private `DurableRunLedger`**. On Owner restart, a `claimed` row becomes `unconfirmed` while the same signed grant may remain cryptographically valid. A signed-only effect admission cannot distinguish a current Claim from an unconfirmed one. Calling the Owner's `quiesced()`, `claim_signed()` or `recover_after_quiescence()` synchronously *while a Worker already holds that exclusive flock* would deadlock.

The test-only reference model in `tests/test_472_effect_admission_d1_contract.py` fixes **required state/order semantics**, not an implementation or deployable security proof. In particular, model booleans are not Owner authorization evidence and must never become API inputs, feature flags or a bearer token.

## D1 target: trusted principals and enforceable effect boundary

| Principal | Exclusive responsibility | What it must **not** do |
|---|---|---|
| **Worker UID** (nonroot) | Present the exact signed Run identity and request a bounded effect session from Owner | Cannot read/modify Owner-private Ledger; cannot obtain raw provider credentials, directly access provider PUT network path, sign grants, rotate or revoke |
| **Owner UID** (separately trusted) | Authenticated session admission, exact private Ledger, signature verification, stable exclusive effect flock, durable one-shot journal, pending Off/rotation | Never accepts Worker-supplied Ledger verdict, current-generation boolean or transferable effect permit; does not store raw Nextcloud credentials or call arbitrary Writer code |
| **Provider broker UID** (separately trusted, **NYI**) | **Sole credential holder and sole network egress path for provider writes**; validates Owner-authenticated dispatch, approved canonical plan, current credential generation, CAS/operation idempotency, readback and durable result | Cannot dispatch a Worker-supplied raw PUT, accept a copied session ID/boolean as proof, change credentials outside Owner-coordinated rotation, or synchronously re-acquire Owner's effect flock |

The broker must **enforce**, not merely witness, admission: without OS/network isolation that prevents the Worker from independently reaching Nextcloud with credentials, the proposed gate is bypassable. Needed future OS policy could be distinct service UIDs, credential ACLs and egress confinement. **None is provisioned in D1/A0.** The broker must authenticate the *connected Owner principal* (for example, an exact `SO_PEERCRED`-verified Unix channel), not trust an arbitrary forwarded request or bearer token; the Worker separately authenticates to Owner. Do not forward raw credentials or arbitrary paths/bytes via either IPC.

**Do not conflate source and credential generations:** The RunIntent.source_generation field is the signed Formatter/Vault source identity, **not** a provider credential generation. The latter must be a separately broker-verified, Owner-private Claim binding and monotonic rotation epoch. The disposable test model represents these as distinct values and verifies that equality to the signed source digest cannot substitute for the claim-time credential binding. The simulated credential epoch and invalidation watermark belong to the shared Owner-wide admission gate, not to individual Run objects, so a rotation invalidates every previously reserved Claim.

**Trusted credential generation:** Owner obtains a fresh generation identity from the separately authenticated broker/credential authority **while holding the effect lease**. Broker independently rechecks its current credential generation immediately before any dispatch. Generation values supplied by Worker, a cached `run.status` or a signed grant alone cannot establish the current credential generation. Broker rotation is prohibited except in an Owner-coordinated operation under the same flock, with a durable monotonic generation/epoch. Every Owner-private Claim reservation must **durably record its broker-verified generation epoch at claim time**; Owner admission compares that immutable Claim epoch with its current durable rotation watermark under flock. Rotation atomically increments the watermark and invalidates all earlier Claims. A return to an older credential digest must **never rearm** an old Claim.

## Proposed linearization and lock ownership (NOT IMPLEMENTED)

Each attempt is identified by a single immutable reviewed identity: **Run ID, operation ID, plan SHA, policy SHA, source generation, account binding SHA, provider proof SHA, receipt root, canonical provider target, precondition ETag, approved before/after hashes, and the Owner-private Claim/credential-generation epoch**. The signed plan hash must bind target, bytes, ETag and budget; no Worker-selected target or PUT payload can be admitted merely by passing a matching Run ID. This identity must be sealed from an immutable approved plan before dispatch. The one-shot key is at least `(run_id, operation_id)` with a durable mapping to this full identity; a new connection may not change it. **Resource-conflict keys** include `(provider account binding, canonical Vault target)` for every path the attempt could affect, independently of Run ID. Unidentified/wider remote effects must quarantine the entire provider account.

**Atomic admission gate (required, NOT IMPLEMENTED):** A single **Owner-wide (not per Run or per process-instance)** private durable journal transaction domain must linearly order **every Run's Begin fence** and **Owner-wide Off/rotation gate closure**, including resource-conflict-index updates and the Claim/rotation epoch. All Owner handlers/processes that can admit effects must share this single authoritative gate, not allocate independent per-session booleans. In the D1/A0 reference model the target/account conflict index also belongs to that **same** Owner-wide gate. No session constructor accepts an independent resource index. A successful test must not depend on a caller manually injecting the same quarantine object into every Run. In the proposed first-host implementation, Begin takes the effect flock first and then briefly begins an Owner-private `BEGIN IMMEDIATE` transaction: re-read the persisted admission-gate state and epoch, deny if Off/rotation already closed it, check unresolved targets, atomically persist the exact one-shot fence/conflict keys, commit with full durability, and release the journal transaction **before** any Begin ACK or broker dispatch. Conversely, Off/rotation must **first** commit a durable `admission_closed` / pending intent in the **same transaction domain**, release the short transaction, **then** attempt to obtain or wait for the effect flock. Never hold this short transaction while waiting on a broker, remote CAS, or the flock. If Begin's fence commits first, Off/rotation remains pending until that already admitted operation settles; if Off/rotation closes the gate first, Begin fails without ACK or dispatch. Recovery starts with gate closed until **Owner-wide boot reconciliation** verifies every pending Claim/attempt; reboot increments a monotonic Owner boot epoch that permanently invalidates every pre-restart Claim, even if another Run session still holds a locally cached claimed state. Per-Run recovery cannot reopen the global gate. These transaction/lock-order rules are source-only specifications; existing `DurableRunLedger` does not implement them.

1. **Claim reservation (existing D0):** Worker may request `run.claim`, but receives no effect capability. New `begin_effect` / broker RPCs are **NYI** and cannot be smuggled through D0 Status.
2. **Lease first:** Owner accepts a newly authenticated Worker connection tied to the exact Run/peer UID; Owner serializes one session and acquires the *same pre-provisioned local exclusive flock inode* as Owner stop/revoke/rotation. **Owner holds that flock, not Worker or broker.** An Owner process must multiplex stop requests and broker responses without re-entering the same lock-taking API.
3. **Authoritative checks under flock:** Owner reads its **private boot-reconciled, exactly `claimed` Ledger row**, verifies externally signed grant, complete immutable Run/plan/policy/operation/binding/proof/target identity, **its durable Claim epoch vs rotation watermark** and obtains a fresh broker-owned credential generation. It also checks a **durable unresolved-resource index** and rejects a new Run ID if it could target the same account/path as an unconfirmed effect. On missing/unavailable/mismatched authority, **deny without dispatch**. No cached Claim or Worker-provided boolean substitutes.
4. **Durable linearization before both ACK and dispatch:** Owner writes/fsyncs a **one-shot effect-attempt fence** in a private journal, whose identity is bound to the exact Run, operation, Claim epoch and resource-conflict keys. States must distinguish `fenced_before_dispatch`, `dispatch_possible`, `verified_settled` and `unconfirmed`. Any ambiguous attempt durably places every affected account/target into the unresolved-resource index **before the lock is released**; the broker must honor the same quarantine, including requests under a different Run ID. The current Ledger status enum does not implement this journal. If journal persistence is ambiguous, **no start ACK, no dispatch and no rearm** until trusted reconciliation. Owner may report effect start only after durable fencing.
5. **Dispatch:** Owner sends a narrow, exact-identity request **directly to the authenticated broker**, over the bound Owner↔broker channel. Broker checks the operation's admitted fenced state via an Owner-authenticated, non-recursive protocol, validates approved plan and current generation, and fsyncs its own pending-dispatch/idempotency record before issuing any provider request. **Broker never acquires or synchronously asks Owner to re-acquire the effect flock.** Worker cannot invoke this dispatch endpoint. All provider writes go through this broker, under a canonical `98-System/**` allowlist, bounded one-file CAS `If-Match` and operation-id checks.
6. **Settlement:** Owner retains the flock across the broker's provider request and trusted CAS/readback/receipt report. The broker's authenticated structured result is only acceptable after it independently validates operation-specific provider finality (not merely matching readback/ETag) and durably writes its own operation result. Owner durably records `verified_settled` and releases the corresponding account/target conflict key in ONE durable Owner-wide transaction before a terminal success ACK. Resource release can never be observed before the terminal journal record; ambiguous journal persistence means unconfirmed with quarantine retained. The test-only immutable Owner journal snapshot models one linearization point; it does NOT prove SQLite durability or actual process-crash safety. The Worker does not decide success by reporting a boolean.
7. **Uncertainty:** A lost Begin ACK, broken channel, fd-close failure, crashed Owner/Worker/broker, ambiguous provider response or absent readback yields `unconfirmed`. An Owner crash invalidates every previously admitted Owner session, including already-fenced dispatch paths, and advances the shared boot epoch; an old session may neither dispatch, terminally settle nor reconcile after restart. The authenticated broker must recheck the Owner session boot epoch and account-wide unresolved quarantine immediately before every effect. An Owner crash may release the kernel flock while a server has already accepted a delayed PUT. Therefore **free flock ≠ settled remote effect**; reboot must examine the durable attempt journal and deny any new effect for that Run **or a different Run with a potentially conflicting provider account/target**, until the independent operation-specific disposition is proven. The broker must refuse such conflicting dispatches too, even if a new Owner misidentifies the Run.
8. **Off/revoke/rotation:** Every stop/rotation completion path, including a direct trusted Owner stop/rotate operation, first **durably prevents new Owner-wide admissions**. No stop or credential-rotation ACK is permitted while any unresolved account-wide quarantine (unknown remote effect) or unidentified target-conflict index remains, even if the active/unconfirmed Run sets are empty. If an effect holds the lock, return **`pending_inflight`**, not a success ACK. If a provider effect is ambiguous after lock release, return **`pending_unconfirmed`** and keep the pending intent; similarly for credential rotation. A bounded timeout is a *non-success pending response*, not a claim that the effect stopped. A fresh credential generation cannot be installed/ACKed out-of-band. Only after an independently verified durable provider outcome can the Owner finalize stop/rotation, with a new monotonic generation invalidating **all** pre-rotation claims permanently.
9. **Reconciliation and identity:** An identical provider file hash or fresh ETag alone does **not prove which in-flight request wrote it**, or that no delayed request remains. Settlement requires trustworthy operation-specific provider/broker idempotency evidence, or an equally reviewed finality/cancellation guarantee. The Owner-private terminal journal must durably distinguish a **verified remote effect** from a **verified never-dispatched/no-effect** outcome for the exact operation, in the same atomic transaction that clears its resource-conflict key. For a fence that was **definitively never dispatched**, the independent Broker journal may establish a separate durable **verified-no-effect** terminal state; a generic matching readback must not fabricate successful settlement of an operation that was never dispatched. If no such evidence exists, the operation and Off/rotation remain **pending**, potentially requiring a Human/operational decision. Do not auto-retry the PUT or turn an unresolved state into a success just because a deadline elapsed.

**Lock/call graph invariant:** Worker → Owner begin on authenticated session; Owner acquires flock → validates private Ledger/current broker generation → persists fence → Owner → broker dispatch (broker **must not reacquire flock**) → broker CAS/readback/durable result → Owner durably settles → releases flock → may ACK stop/rotation. Owner stop/rotation requests must not hold a second mutex while waiting for this flock if the active session needs that mutex to complete. D1/B0 must explicitly document concurrency lanes and crash/fd ownership, rather than reusing the existing D0 one-command listener for a long-lived effect lease.

**Multi-host limitation:** An ordinary local `flock` is not cross-host authority. The first implementation scope is one Owner host with cooperating processes on one approved local filesystem; multi-host Writers or credential rotation are out of scope.

## Disposable reference-model tests

`tests/test_472_effect_admission_d1_contract.py` checks exact synthetic identity, Owner boot/claim checks, pre-dispatch durable attempt/ACK order, Worker denial of direct broker dispatch, no double or second-connection effect, trusted generation mismatch and **durable Claim epoch/rotation watermark** (including return to an old generation), **cross-Run conflicting-target quarantine**, pending Off/rotation vs successful ACK (including direct-stop fencing and account-wide unknown-effect quarantine), channel loss, reconnect and ambiguous readback, no blind retry, and explicit operation-specific reconciliation (or independently verified no-dispatch terminality) before completion. It separately rejects ordinary readback+receipt without operation-specific finality, preserves quarantine on an ambiguous terminal-journal commit, and models terminal settlement and conflict-key release as ONE immutable Owner-wide snapshot. It also exercises **existing** `DurableRunDrain`/Owner lock and Ledger reboot/signed-grant divergence on disposable signed fixtures. All provider/credential/broker behavior in the model is abstract; no real effect is made.

**Evidence boundary:** `RunStatusObservation`, test-only truth values, event order lists and passing tests are not security grants. No module in `src/obsidian_automation/` imports this reference model. Prior genuine distinct-UID D0 CI is separate evidence, not a combined D1 admission test. These tests cannot show durability, timeout-safe provider finality, broker egress confinement, true UID isolation or cross-host correctness.
