# Semantic Hybrid Retrieval v1

## Purpose

Semantic Hybrid Retrieval v1 is Semantic Planner Phase C / issue #201.

It compares lexical BM25, semantic-vector, and hybrid retrieval over the same
Semantic Corpus chunk population before any production Planner selection is
changed.

This stage does **not** replace the existing Knowledge-only BM25 path used by the
Evaluator. The current Evaluator retrieval remains unchanged.

## Retrieval population

All three modes operate over chunks from one exact
[Semantic Embedding Index v1](semantic-embedding-index-v1.md).

This is important: the benchmark does not compare the old Knowledge-only BM25
corpus with a wider vector corpus. BM25 is recomputed over the same eligible
Daily / Idea / Project / Project Note / Knowledge chunks used by vector ranking.

Each candidate remains bound to:

- source path;
- source kind;
- exact source SHA-256;
- exact chunk identity;
- chunk content SHA-256;
- embedding request/result identity;
- semantic index identity.

Lexical text is the exact bounded chunk text already stored in the immutable
embedding request. It is not regenerated by a model.

## Query embedding authority

Query vectors use the same Reader -> Embedder -> Reader boundary as corpus
embedding.

```text
Reader
  semantic index + query
      |
      v
04-Index/semantic-embedding-requests/
  <sha>.semantic-query-embedding-request.json
      |
      | read-only
      v
obsidian-ai-embedder
  GET /api/tags
  POST /api/embed
      |
      v
04-Index/semantic-embedding-results/
  <sha>.semantic-query-embedding-result.json
      |
      | read-only
      v
Reader
  rank against exact semantic index
```

The query request binds the semantic index SHA, provider/adapter, exact model
identifier/revision, vector dimension/encoding, query bytes, and query SHA.

Embedder still cannot read the semantic index or Vault. The request contains
only the bounded query text needed for inference.

## Retrieval modes

### BM25

BM25 uses the existing tokenizer contract:

```text
nfkc-ascii-cjk-bigram-v0
```

but computes document frequency and BM25 scores over the eligible Semantic
Corpus chunks for that query/filter set.

BM25-only score:

```text
score = raw_bm25 * source_kind_weight
```

Chunks with zero BM25 score are omitted from BM25-only results.

### Vector

Vector ranking uses cosine similarity against the exact query embedding.

```text
score = cosine(query_vector, chunk_vector) * source_kind_weight
```

A zero-norm query is rejected. A zero-norm candidate receives cosine score 0.

### Hybrid

Raw BM25 and cosine are not directly comparable, so Hybrid normalizes each
component per query.

```text
lexical_normalized = bm25 / max_bm25
semantic_normalized = (cosine + 1) / 2

hybrid =
  source_kind_weight
  * (
      lexical_weight * lexical_normalized
      + vector_weight * semantic_normalized
    )
```

Initial offline comparison weights:

```text
lexical_weight = 0.60
vector_weight  = 0.40
```

These weights are benchmark parameters, not production authority. Issue #202
owns later selection-policy decisions.

Tie-breaking is deterministic:

1. final score descending;
2. raw lexical score descending;
3. raw cosine score descending;
4. source path case-folded;
5. source path exact;
6. chunk id.

## Metadata filters

Reader may filter the candidate population before scoring by:

- `source_kinds`;
- `workspaces`;
- `projects`;
- `idea_statuses`;
- `project_statuses`;
- `created_from` / `created_to`;
- Knowledge `category`;
- Knowledge `maturity`;
- Knowledge `source_type`.

Date filters use ISO `YYYY-MM-DD`. Daily uses its derived note date; Idea uses
`created`. A source without applicable date metadata does not pass a requested
date filter.

Project status means:

- Project Entry: its own `status`;
- Project Note: the already-resolved parent `project_status`.

Filters are selection constraints, not canonical mutations.

## Source-kind weighting

Each source kind defaults to weight 1.0:

```text
daily
idea
project
project-note
knowledge
```

A caller may provide finite weights in `0..10`.

Weighting changes ranking only. It does not change eligibility, source metadata,
or canonical Vault state.

## Canonical re-read before use

A stored semantic index is derived state, not source authority.

Before returning ranked chunks for downstream use, Reader:

1. verifies the Semantic Corpus is still current against the pull-only mirror;
2. resolves each selected source/chunk from the exact corpus manifest;
3. re-reads canonical mirror bytes;
4. rechecks exact source SHA, chunk range, chunk SHA, and chunk identity.

A stale source therefore fails before a ranked chunk may be persisted into a
future Context Bundle.

Phase C does not yet create Generation Context from these results. The next
stage is [Semantic Selection and Novelty v1](semantic-selection-novelty-v1.md),
which uses the same exact-index retrieval signals to produce versioned,
content-addressed Selection Records.

## Benchmark contract

Schema:

```text
schemas/semantic-retrieval-benchmark-v1.schema.json
```

Starter shape:

```text
examples/ai/semantic-retrieval-benchmark.example.json
```

Replace every placeholder path with an exact source in the selected Semantic
Corpus before using the example as production evidence.

The benchmark uses one fixed query corpus for all three modes.

Required case categories:

```text
exact-technical
semantic-paraphrase
project-local
daily-knowledge
idea-project
cross-domain-bridge
```

Each case contains:

- stable case id;
- one category;
- exact query text;
- one or more relevant source paths;
- optional metadata filters.

The benchmark is content-addressed after canonical parsing.

### Benchmark flow

Reader prepares exact query requests:

```bash
sudo -u obsidian-ai-reader \
  obsidian-semantic-retrieval benchmark-prepare \
  --ai-root /var/lib/obsidian-ai/state \
  --semantic-index-sha <semantic-index-sha256> \
  --benchmark benchmark.json
```

Embedder resolves the pinned model once and embeds all benchmark queries:

```bash
sudo -u obsidian-ai-embedder \
  obsidian-semantic-retrieval benchmark-embed \
  --ai-root /var/lib/obsidian-ai/state \
  --plan-sha <benchmark-plan-sha256> \
  --base-url http://127.0.0.1:11434
```

Reader evaluates all three modes:

```bash
sudo -u obsidian-ai-reader \
  obsidian-semantic-retrieval benchmark-evaluate \
  --ai-root /var/lib/obsidian-ai/state \
  --vault-root /var/lib/obsidian-ai/vault \
  --semantic-index-sha <semantic-index-sha256> \
  --benchmark benchmark.json \
  --plan-sha <benchmark-plan-sha256> \
  --result-set-sha <benchmark-result-set-sha256> \
  --top-k 3
```

## Metrics

Reports include, for each mode:

- top-1 accuracy;
- macro recall@K;
- mean reciprocal rank;
- separate metrics for exact-technical cases;
- separate metrics for semantic cases;
- per-case top results with raw BM25 and cosine component scores.

Chunk results are collapsed to the first occurrence of each source path for
source-level benchmark metrics. Ranking output itself remains chunk-level.

## Acceptance gate

The Phase C report explicitly computes:

```text
hybrid semantic recall@K > BM25 semantic recall@K
AND
hybrid exact-technical top1 >= BM25 exact-technical top1
```

Both conditions must hold for `acceptance.passed=true`.

This report is evidence for a later production decision; it does not
automatically switch Planner behavior.

A benchmark failing this gate is useful evidence. Do not tune against one result
by silently changing the benchmark corpus. Update ranking policy only through a
versioned change and rerun the unchanged benchmark plus any newly added cases.

## Single-query diagnostic flow

Prepare:

```bash
sudo -u obsidian-ai-reader \
  obsidian-semantic-retrieval query-prepare \
  --ai-root /var/lib/obsidian-ai/state \
  --semantic-index-sha <semantic-index-sha256> \
  --query 'your query'
```

Embed:

```bash
sudo -u obsidian-ai-embedder \
  obsidian-semantic-retrieval query-embed \
  --ai-root /var/lib/obsidian-ai/state \
  --request-sha <query-request-sha256> \
  --base-url http://127.0.0.1:11434
```

Rank:

```bash
sudo -u obsidian-ai-reader \
  obsidian-semantic-retrieval rank \
  --ai-root /var/lib/obsidian-ai/state \
  --vault-root /var/lib/obsidian-ai/vault \
  --semantic-index-sha <semantic-index-sha256> \
  --request-sha <query-request-sha256> \
  --result-sha <query-result-sha256> \
  --mode hybrid \
  --top-k 8
```

Optional filter JSON may contain any subset of the documented filter fields.
Optional source-kind weight JSON is a flat object such as:

```json
{
  "daily": 0.8,
  "idea": 1.2,
  "project": 1.1,
  "project-note": 1.0,
  "knowledge": 1.0
}
```

## Non-goals

Phase C does not:

- change the automatic Input Planner;
- replace Evaluator Knowledge retrieval;
- enable semantic novelty gating;
- choose generation objectives;
- change generation cadence;
- mutate Idea / Project / Knowledge canonical state;
- make ANN/vector database state authoritative.

Those remain later Semantic Planner phases.
